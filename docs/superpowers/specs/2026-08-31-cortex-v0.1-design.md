# Cortex v0.1 Architecture and Design

**Status:** Proposed design approved for specification writing; pending written-spec review  
**Date:** 2026-08-31  
**Scope:** Cortex v0.1 architecture and its explicitly constrained end-to-end vertical slice

## 1. Purpose and non-negotiable principles

Cortex is a local-first, terminal-native personal digital brain. It stores and operates on personal knowledge, notes, tasks, memories, and their evidence. Cortex, rather than an LLM, is the canonical system of record. Models and MCP clients reason over a constrained, audited Cortex capability surface; they do not own state or bypass validation.

v0.1 must prove that one canonical local state is safely usable by three interfaces: the `brain` CLI, a local inference-driven agent, and ChatGPT through MCP. It must remain useful offline and when the local model is unavailable.

The following invariants govern every later implementation decision:

1. Durable user knowledge is exportable.
2. Every AI-generated memory has immutable provenance.
3. Every state change passes the Cortex policy layer.
4. Every destructive action has an explicit policy decision and an audit record.
5. Retried requests must not duplicate side effects.
6. Domain and business logic are independent of a model provider.
7. Embeddings supplement, never replace, lexical retrieval.
8. AI-derived content never silently replaces source evidence.
9. External content is data, never privileged instruction.
10. Core notes, task, memory, and search functions work without internet.

## 2. Product boundary and v0.1 success criteria

There is no GUI, web dashboard, desktop application, mobile application, or required TUI in v0.1. The product interfaces are a scriptable CLI and MCP. `brain tui` is a future option only.

The v0.1 release is successful when the following state is shared by CLI, local agent, and ChatGPT MCP:

```text
brain ask "Remember that Cortex uses Nemotron as its local AI."
  -> validated, audited memory creation with provenance

brain ask "What local AI did we choose?"
  -> hybrid retrieval result citing the memory and its source

ChatGPT asks the same question through MCP
  -> the same canonical record and provenance are returned
```

The first slice also supports creation, update, deletion, restoration, and search of notes, tasks, and memories, subject to capability grants. Deletion is recoverable: normal queries omit tombstoned records, restore is an audited command, and irreversible purge is not available in v0.1.

## 3. Chosen architecture

Cortex is a modular monolith with a deliberately thin, separately runnable MCP transport adapter. It is not a microservice system.

```text
                   ChatGPT
                      |
               remote MCP traffic
                      |
          outbound-only secure tunnel
                      |
             cortex-mcp-gateway
                      |
        authenticated local IPC client
                      |
                    cortexd
                      |
   application commands/queries + policy + audit
                      |
      domain invariants, repositories, search, inference
                      |
                    SQLite

brain CLI ----------------------^  (same local IPC and application surface)
local agent --------------------^  (same capability catalog and policy)
```

`cortexd` is the only process that opens the SQLite database for mutation. It owns migrations, authorization decisions, audit writes, business commands, queries, and retrieval. The `brain` CLI is an authenticated local IPC client. `cortex-mcp-gateway` accepts MCP transport requests, authenticates them, obtains a Cortex principal, applies transport limits, and calls the same application boundary; it contains no domain rules or storage access.

ChatGPT cannot directly connect to a private local MCP server. v0.1 therefore uses an outbound-only encrypted tunnel: a local gateway initiates the connection and no public listener is exposed from the Cortex host. The relay is a stateless transport boundary and never receives database access, storage credentials, or a responsibility to authorize Cortex actions. The exact tunnel vendor is configuration, not a domain dependency.

## 4. Workspace and dependency direction

The initial Rust Cargo workspace contains only boundaries justified by the vertical slice:

```text
crates/
  cortex-domain/       strong identifiers, domain objects, invariants, errors
  cortex-application/  commands, queries, capability catalog, policy orchestration
  cortex-storage/      SQLite repositories, migrations, secret-store port adapter
  cortex-search/       FTS, embeddings, hybrid ranking, provenance-aware results
  cortex-inference/    inference/embedding provider ports and local-server adapter
  cortex-mcp/          MCP request/response and transport adaptation
apps/
  cortexd/             process composition and local IPC server
  brain/               Clap CLI and machine-readable output
  cortex-mcp-gateway/  Streamable HTTP MCP server and tunnel client
```

Dependencies point inward: interface applications and infrastructure adapters depend on application/domain contracts; domain depends on neither SQLx, MCP, HTTP, nor a model SDK. Notes, tasks, memories, provenance, policy, audit, and scheduling primitives are domain/application modules, not empty crates. New crates require a distinct ownership boundary and independently useful public contract.

Rust uses Tokio, Serde, SQLx/SQLite, Clap, tracing, rustls, Reqwest, Axum where required for local transport, and RMCP for MCP transport. Toolchain policy, exact versions, feature flags, MSRV, and lint configuration are set in the implementation plan after verifying compatibility; `unsafe` is forbidden where practical and warnings are treated as defects.

## 5. Domain model and ownership

All durable entities have a UUIDv7 identifier, `WorkspaceId`, monotonic `Revision`, creation/update timestamps, and lifecycle state. UUIDv7 provides sortable globally unique IDs suitable for later offline multi-device operation. v0.1 creates one default workspace and owner, but it never relies on an implicit global user.

Core types and concepts are:

| Concept | Responsibility | Key invariants |
| --- | --- | --- |
| `Workspace` | Ownership and future tenancy boundary | Every durable user entity belongs to one workspace. |
| `Principal` | Authenticated actor: owner, paired ChatGPT identity, or future service/user | Every request is attributed to a principal. |
| `Note` | User-authored long-form knowledge | Content remains separate from AI memory assertions. |
| `Task` | Deterministic actionable work item | Completion is a validated state transition; due dates are data, not schedule decisions. |
| `MemoryAssertion` | A concise retrievable claim | Has provenance; cannot replace its source; may be superseded, forgotten, deleted, or conflict with another assertion. |
| `Source` | Immutable evidence/provenance record | Captures origin, creation method, actor, and source reference without duplicating secrets. |
| `CapabilityGrant` | Policy authorization from a principal to a capability in a workspace | Grants are explicit and scope every mutation. |
| `AuditEvent` | Append-only action evidence | Redacted; records decision/outcome without storing sensitive payloads. |

`MemoryAssertion` has normalized subject/predicate/object-or-text fields, a source set, creation method (`explicit_user`, `agent_tool`, and later `import`), and a lifecycle. A correction creates a new assertion with a `supersedes` relation; it does not mutate or hide original evidence. Conflicting active claims share a normalized fact key but retain separate records and are returned as a conflict set. Cortex never lets a model silently choose a winner.

Lifecycle is `active` or `deleted` at the entity level. Memory additionally has semantic status such as active, superseded, or forgotten. Standard retrieval excludes deleted and forgotten/superseded assertions unless an explicit history query asks for them. v0.1 has no irreversible purge.

## 6. Application capabilities and policy

The application layer is the shared capability boundary. It exposes typed commands and queries, not generic RPC strings:

```text
Queries:  note.search, task.list, memory.search, knowledge.retrieve
Commands: note.create/update/delete/restore
          task.create/complete/update/delete/restore
          memory.create/correct/delete/restore
```

Each catalogued capability declares input and output types, required grant, mutability, destructive classification, audit classification, idempotency semantics, and an MCP-safe description. CLI commands, local-agent tools, and MCP tools adapt to these same contracts.

The MCP gateway derives `PrincipalId` from authenticated pairing context. It never trusts a client-supplied principal or workspace ID. `cortexd` evaluates the final policy decision, validates input, checks expected revision for mutations, writes the domain change and audit event transactionally, and returns a typed result.

v0.1 has a single owner but is multi-user-ready: all records are workspace-scoped, all requests have principals, and grants are first-class. The paired ChatGPT principal is granted read, write, delete, and restore capabilities by the owner’s configuration. This is an explicit stored policy decision, so normal operations need no local interactive confirmation. A delete still requires a matching destructive capability grant, active target, expected revision, and audit event. Future policies may add time, entity, connector, or approval constraints without changing command implementations.

## 7. Persistence, secrets, and audit

SQLite is the local durable store. `cortexd` enables WAL and foreign-key enforcement, applies ordered and checksummed SQLx migrations before serving requests, and uses transactions for state changes plus their audit event. Repository implementations are replaceable infrastructure behind application-owned ports.

At minimum, schema design includes workspace/principal/grant tables; note/task/memory/source/provenance-relation tables; FTS content/index metadata; embedding metadata/blobs; deletion/revision columns; operation-id deduplication records; and append-only audit events. A mutation has `operation_id`, `entity_id`, `base_revision`, `new_revision`, actor, timestamp, and operation semantics. This supports idempotent retries and is compatible with a later sync operation log without prematurely implementing CRDTs.

Credentials never enter ordinary SQLite fields. A `SecretStore` port resolves opaque secret references through the platform keychain or secure secret store. Models, audit events, and MCP output never receive raw credential values. Configuration is local and exportable without secret material.

Audit events include principal, capability, target IDs, correlation ID, policy outcome, result class, and redacted metadata. They intentionally exclude raw notes, memory text, credentials, raw tool prompts, and verbose storage errors by default. Diagnostic payload capture is opt-in and separately redacted.

## 8. Hybrid search and embeddings

Unified retrieval covers active notes, tasks, memories, and permitted source excerpts. It returns a typed result including entity type, snippet, score explanation, and source/provenance citations.

1. SQLite FTS5 produces lexical candidates.
2. The configured local embedding provider produces embeddings for indexable content.
3. Cortex stores dimension-validated `f32` blobs with model identifier, version, content hash, and index state.
4. A bounded in-process cosine scan produces semantic candidates at personal-data scale.
5. Deterministic reciprocal-rank fusion combines lexical and semantic ranks, then lifecycle, workspace, and capability filtering is applied.

This is real end-to-end semantic retrieval in v0.1, not a placeholder. It avoids a separate vector database and premature reliance on an immature extension. The vector-scan implementation is behind a search index port; a later approximate/vector-index implementation can replace it without changing capability callers. If embedding inference is unavailable, lexical retrieval remains available and marks the semantic leg degraded.

## 9. Inference and agent loop

`InferenceProvider` and `EmbeddingProvider` are ports. The first adapter targets a configured OpenAI-compatible local model server, with Nemotron as the default profile. Cortex does not host the model server, and no domain type depends on Nemotron or any provider-specific payload.

`brain doctor` validates configured endpoints, reachability, model/profile configuration, and embedding dimensions but no startup action requires a live model. The system’s deterministic capabilities continue when inference is offline.

The local agent receives only its allowed capability catalog and uses structured requests. It is bounded by tool schema validation, iteration limit, timeouts, duplicate-call detection, request/cost bounds, and policy checks. Cortex validates resulting commands just as it validates MCP input. Malformed model output becomes a typed inference error; it cannot be persisted as domain data.

## 10. MCP and remote connectivity contract

`cortex-mcp-gateway` uses versioned Streamable HTTP MCP transport and adapts it to the application capability catalog. Initial MCP tools cover search/retrieval and the approved note/task/memory create, update, delete, and restore commands. Read-only resources expose safe entity/source views. Business logic, authorization, persistence, and ranking remain outside handlers.

The gateway authenticates a paired remote client using OAuth/OIDC-compatible identity, maps that identity to a local principal, and applies request-size, host/origin, rate, session, and transport timeout limits. It forwards over authenticated local IPC to `cortexd`; `cortexd` independently authorizes the request.

MCP responses use stable public error categories and do not reveal file paths, SQL failures, internal identities, secrets, or raw diagnostic data. Tool input schemas omit principal/workspace selection. Every mutation returns canonical entity ID, revision, lifecycle, and audit correlation ID suitable for safe retries.

## 11. Error handling and observability

Error types are structured and deliberately classified: validation; not-found; conflict/stale revision; permission denied; policy denied; storage failure; migration failure; inference unavailable; inference timeout; malformed model output; MCP protocol error; connector failure; scheduler conflict; and internal invariant violation. CLI renders human and machine-readable forms; MCP maps them to safe public messages and codes; tracing retains cause chains locally.

Structured tracing propagates a correlation ID across CLI, IPC, gateway, daemon, application command/query, policy decision, storage operation, search leg, and inference request. Local diagnostics include `brain status`, `brain doctor`, and `brain logs`. Telemetry is local by default and never exports personal data without explicit configuration.

## 12. Security and threat model requirements

The implementation must maintain a threat model covering malicious MCP clients; prompt injection; malicious documents and connector data; compromised API credentials; local privilege boundaries; accidental destructive actions; poisoned memory; hallucinated tool arguments; audit leakage; unauthorized remote access; and future relay compromise.

Key mitigations are: local-only database ownership; outbound-only tunnel; paired authenticated principals; least-privilege capability grants; final local policy enforcement; input bounds and schemas; optimistic concurrency; idempotency keys; provenance; prompt/data boundary treatment; secret-store integration; redacted audit/log output; and safe external error mapping. Security-sensitive integrations and importers are deferred until their dedicated threat-model extensions exist.

## 13. Testing and evaluation requirements

Implementation is test-driven. No core test requires a live proprietary model service; optional integration tests are explicitly isolated.

| Area | Required test examples |
| --- | --- |
| Domain | invalid IDs/dates, task transitions, lifecycle/restore, revision conflicts, memory correction, conflict sets, provenance-required memory |
| Storage | fresh migration, upgrade migration, foreign-key constraints, transaction rollback, idempotent operation retry, repository round trip |
| Search | FTS match, semantic-only match, deterministic rank fusion, permissions/lifecycle filters, embedding-dimension rejection, degraded provider |
| Policy | allowed/denied grants, delete grant enforcement, principal spoofing rejection, audit redaction |
| Agent | valid structured call, malformed call, unknown tool, duplicate call, iteration/timeout exhaustion, unavailable provider |
| MCP | schema contracts, identity propagation, safe public errors, remote mutation reaches shared state, authorization failure |
| CLI/IPC | stable JSON output, nested command parsing, daemon-unavailable error, same state as MCP |

The eval suite includes curated, versioned cases for memory candidacy, non-memory rejection, entity reference resolution, source support, contradiction detection, tool selection, and approval/policy classification. Models may propose; deterministic Cortex code validates and decides.

## 14. Explicit v0.1 exclusions and v0.2+ roadmap

v0.1 deliberately excludes first-class projects and relations, calendar/event scheduling, external connectors, automation, skills, sync, multi-user server operation, vector indexing beyond bounded scan, model hosting, irreversible purge, public inbound server exposure, and GUI/TUI work. These are deferred to protect the foundational vertical slice, not abandoned.

| v0.2+ area | Prerequisites preserved in v0.1 | Future boundary and acceptance condition |
| --- | --- | --- |
| Projects and relations | workspace/entity IDs, task ownership, typed commands | Add `Project` and typed entity relations; tasks can link to projects; no generic graph required. |
| Calendar and deterministic scheduling | task due-date fields, policy/audit, domain scheduling module location | Add events, constraints, availability, deterministic planner, conflict explanations, and `brain today`. |
| Connectors | source/provenance model, secret-store port, capability boundary | Provider adapters expose authenticate/capabilities/sync/search/execute without provider types in domain. |
| Automation and skills | capability catalog, policy, audit, idempotency | Define declarative workflow/triggers and bounded execution; every side effect retains policy/audit semantics. |
| Sync and remote Cortex | UUIDv7, revisions, operation IDs, device-ready mutation metadata | Add device identity, sync log/transport, conflict policy, and idempotent replication without retrofitting entity IDs. |
| Multi-user server mode | workspace IDs, principals, grants, owner-scoped records | Add user/workspace administration, tenant isolation, invitations, and server authentication; preserve v0.1 single-owner behavior. |
| Vector indexing | `SearchIndex` port, embedding metadata/content hashes | Replace bounded scan with a tested index backend while preserving ranking, filters, and citations. |
| Irreversible purge | tombstones and audit records | Add retention policy, export/warning checks, a separately authorized purge capability, and verifiable deletion semantics. |

## 15. Architecture decision records

The implementation creates these ADRs before or with the tasks that establish their boundaries:

1. Rust as primary language.
2. Modular monolith architecture.
3. Local-first architecture.
4. SQLite as initial persistent store.
5. Shared Cortex application/capability boundary.
6. MCP as first-class external AI protocol.
7. Local inference through provider abstraction.
8. Nemotron as default profile, not architectural dependency.
9. AI memory requires provenance.
10. Capability-based authorization.
11. Deterministic scheduling.
12. Hybrid retrieval rather than vector-only search.
13. Local model server separated from `cortexd`.
14. UUIDv7 globally unique IDs.
15. CLI-to-daemon authenticated local IPC.
16. Outbound-only bridge for ChatGPT MCP access.
17. Single-owner v0.1 with multi-user-ready ownership and principals.
18. Recoverable deletion lifecycle.
19. Bounded SQLite vector scan behind a future index port.

## 16. Rejected approaches

- A GUI-first product: conflicts with terminal-native scope.
- A separate implementation for CLI, local agent, and MCP: would violate the shared capability/source-of-truth requirement.
- A public inbound `cortexd` endpoint: expands attack surface and contradicts the local-first transport decision.
- A remote Cortex-aware relay: gives remote infrastructure responsibility for personal-data policy and ownership.
- A vector database or generic knowledge graph in v0.1: adds operational complexity before it proves retrieval value.
- One crate per hypothetical subsystem: creates speculative, empty abstractions and cyclic-dependency risk.
- A fully autonomous agent or multi-agent swarm: violates explicit policy and bounded-action requirements.

## 17. Implementation sequencing constraint

The implementation plan must use TDD, small independently testable tasks, exact files/interfaces/test cases/commands, frequent commits, and no placeholders. It must produce the smallest useful vertical slice early: domain/persistence/capability/policy/audit; CLI/IPC; notes/tasks/memories/provenance; FTS/embeddings/hybrid retrieval; local agent; then the MCP gateway/tunnel integration. Each task must be independently reviewable and preserve the stated security invariants.
